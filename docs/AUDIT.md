## 1. Безопасность

### 1.1 Модель доступа — что сделано хорошо

Это не «дырявый проект», база защищена аккуратно, и это стоит зафиксировать:

- RLS включён на всех семи таблицах `booking_*`.
- `booking_busy_intervals` отдаёт только `station_id / room_id / время` — ФИО и
  телефоны других клиентов недоступны анонимам вообще.
- `booking_discounts` намеренно без политик — только через
  `booking_validate_discount()`.
- Helper-функции (`booking_station_price`, `booking_day_kind`,
  `booking_resolve_discount`, `booking_sync_item_activity`, `booking_quote`)
  сняты с публичного API через `revoke`.
- Все `SECURITY DEFINER` функции имеют `set search_path` — классический вектор
  подмены схемы закрыт.
- EXCLUDE-констрейнт `booking_no_overlapping_items` делает двойную бронь
  невозможной на уровне БД, а не на уровне «клиент проверил» — гонка двух
  вкладок обрабатывается корректно (`23P01` → `_handleConflict`).
- Админка за Supabase Auth + allowlist `booking_staff` + `booking_is_staff()`.
- anon **не имеет** `select` на `booking_orders` — персональные данные закрыты.

### 1.2 C1 — прямая запись анонимом мимо RPC (высокий)

```sql
grant insert on public.booking_orders, public.booking_order_items to anon;
```

`booking_create_order` — `SECURITY DEFINER`, ей RLS и гранты не нужны: она
работает от владельца. Значит эти `grant insert` — лишняя, параллельная дверь
с более слабой проверкой. Через PostgREST (`POST /rest/v1/booking_order_items`)
с публичным anon-ключом можно:

- **поставить `price = 0`** — RLS проверяет время, длительность, зал, но не цену;
- **смешать клубы** — политика на `booking_order_items` не связывает
  `order_id` с `club_id` заказа, станция проверяется сама по себе;
- **подставить `source = 'staff'`** — политика на `booking_orders` не ограничивает
  `source`, искажается вся аналитика по источникам;
- **дописать позицию в чужую бронь** — владельца у заказа нет, проверки
  «этот order создал я» не существует. Нужен UUID чужого заказа, но он попадает
  в `postMessage` события `vr-booking:success` и в localStorage.

Обходные проверки в RPC (пакеты, привязка станций к клубу, скидка по числу
станций) через эту дверь просто не выполняются.

**Что делать:**

```sql
revoke insert on public.booking_orders, public.booking_order_items from anon;
drop policy if exists booking_orders_anon_insert on public.booking_orders;
drop policy if exists booking_order_items_anon_insert on public.booking_order_items;
```

Единственный путь создания брони остаётся `booking_create_order()`. Поверхность
атаки сжимается до одной функции с полной валидацией. Риск изменения нулевой:
виджет уже ходит только через RPC/Edge Function.

### 1.3 C2 — нет защиты от массовой фиктивной брони (высокий, практический)

Самая реальная угроза для бизнеса. Сейчас:

- Edge Function: `authorized()` при пустом `BOOKING_INTAKE_KEY` принимает **любой**
  непустой Bearer. Шлюз требует anon-JWT — но он публичный, лежит в бандле
  (`booking_config.dart:22`).
- `CORS_ORIGIN` по умолчанию `*` — вызывать можно откуда угодно, в т.ч. curl'ом.
- Валидация клиента: имя ≥ 2 символа, телефон ≥ 5 символов. Ни капчи, ни
  подтверждения телефона, ни лимита броней на номер/IP.

Скрипт на 200 строк занимает все 24 станции обоих клубов на 30 дней вперёд
за минуты. Клуб узнает об этом, только когда никто не придёт.

**Что делать (по возрастанию стоимости):**

1. **Лимит в БД** — самое дешёвое и эффективное. В начале `booking_create_order`:
   ```sql
   if (select count(*) from public.booking_orders
        where client_phone = btrim(p_client_phone)
          and created_at > now() - interval '1 hour') >= 3 then
     raise exception 'RATE_LIMITED' using errcode = 'P0001';
   end if;
   ```
   Плюс общий лимит «не больше N будущих активных броней на один телефон».
2. **Задать `BOOKING_INTAKE_KEY`** и собирать виджет с
   `--dart-define=BOOKING_API_KEY=<этот ключ>` — тогда произвольный anon-ключ
   уже не подойдёт (ключ всё равно в бандле, но это отсекает скан по чужим
   Supabase-проектам).
3. **Сузить `BOOKING_CORS_ORIGIN`** до списка боевых доменов (нужна доработка
   функции под список — сейчас поле одно).
4. **Подтверждение телефона кодом** для броней > N станций — если griefing
   станет реальностью.
5. Технический минимум для расследования: писать `ip` / `user_agent` в
   `booking_orders` (Edge Function их видит).

### 1.4 Клиентский пароль в админку — не защита (средний, но осознанный)

`BookingConfig.adminGate = 'vr2026'` лежит в `main.dart.js` открытым текстом,
`_AdminDoor._open` сравнивает строки в браузере. Обходится за 10 секунд
(`?admin=1` в адресной строке). В коде это честно задокументировано как «заслон
от случайных нажатий», и в боевой сборке за ним стоит Supabase Auth — тогда всё
корректно. **Но:** в текущей демо-сборке (`USE_MOCK=true`) `AdminAuthGate.authEnabled == false`,
и админка открывается вообще без пароля. Если демо-сборка окажется на публичном
домене — панель персонала открыта миру.

**Что делать:** никогда не выкладывать mock-сборку наружу; в `docs/DEPLOY.md`
добавить явный чек-лист «`USE_MOCK` не задан». Пароль в бандле — оставить как
есть, он делает ровно то, что заявлено.

### 1.5 Заголовки и встраивание (средний)

- Нет `Content-Security-Policy`. Для приложения, которое грузит только свои
  ассеты и один домен API, CSP пишется тривиально и закрывает целый класс атак.
- Нет `frame-ancestors` — виджет может встроить **любой** сайт. Для фишинга
  («забронируй VR, введи телефон») это готовая площадка. `X-Frame-Options`
  ставить нельзя (нужен iframe), но `frame-ancestors` со списком доменов — можно.
- Нет `Referrer-Policy`, `Permissions-Policy`.
- `postMessage(msg, '*')` в `web/index.html:31` — событие `vr-booking:success`
  с `orderId`, числом станций и суммой уходит любому родительскому окну.
  Не критично (не ПДн), но `targetOrigin` стоит сузить.

Предлагаемый `_headers` / `.htaccess`:

```
Content-Security-Policy: default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self' https://cpjmirlujtfuzvdnysyx.supabase.co https://cpjmirlujtfuzvdnysyx.functions.supabase.co; frame-ancestors 'self' https://effectvr.ru https://vrayarena.ru https://*.vk.com https://*.vk.ru
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: geolocation=(), microphone=(), camera=(), payment=()
```

### 1.6 Внешняя зависимость от Google Fonts (найдено при внедрении CSP)

Как только CSP заработала, выяснилось, что **CanvasKit в рантайме тянет Noto Sans
с `fonts.gstatic.com`** — fallback для глифов, которых нет в Archivo. Раньше это
было не видно: запрос уходит молча.

Последствия:

- виджет зависит от домена Google **в рантайме**, а `fonts.gstatic.com` из РФ
  доступен не всегда — это ровно та причина, по которой в `DEPLOY.md` отказались
  от Cloudflare;
- каждый посетитель виджета делает запрос к Google (лишний трафик и след).

Проверено: при заблокированном `fonts.gstatic.com` интерфейс отрисовывается
**корректно** — видимые символы (`·`, `–`, `₽`, кириллица) покрыты Archivo.
То есть зависимость не блокирующая, но лишняя. Один явный потребитель Noto был
найден и убран: символ `✓` в подписи плитки станции заменён на `Icons.check`
из бандла. Остаточные запросы (3 шт. на загрузку) — превентивный fallback
CanvasKit.

`fonts.gstatic.com` разрешён в CSP, чтобы ничего не сломать. **Задача:** снять
зависимость полностью — проверить набор глифов Archivo и либо не использовать
непокрытые символы, либо добавить локальный сабсет.

### 1.7 Мелочи и «на вырост»

- **Нет лимита на число отрезков** в новой `booking_create_order`. Каждый отрезок
  проверяется (60–300 мин, рабочие часы, не в прошлом), но их может быть 50 —
  и одна «бронь» растянется на весь день. Добавить
  `if v_seg_count > 5 then raise exception 'BAD_DURATION'`.
- **Нет проверки, что отрезки не пересекаются между собой** и идут подряд.
  EXCLUDE поймает пересечение по станции, но `[11:00–12:00] + [20:00–21:00]`
  в одной «броне» пройдёт.
- **`v_min_start` в новой RPC вычисляется и нигде не используется** — мёртвая
  переменная (`20260910120000`, строка 113).
- **Персонал видит брони обоих клубов** — `booking_orders_staff_read` не
  разграничивает по клубу. Для двух клубов приемлемо; при росте — добавить
  `booking_staff.club_id`.
- **Нет журнала действий персонала.** Кто отменил бронь, кто поднял цену —
  не восстановить. Нужна таблица `booking_audit_log`, заполняемая триггером.
- `.htaccess` ставит `immutable` на год **всему**, кроме входных файлов. Ассеты
  Flutter (`assets/fonts/Archivo.ttf`, `assets/AssetManifest.json`) хэша в имени
  не имеют — при смене шрифта пользователи год не увидят обновления.
  Исключить `/assets/*` из `immutable` или ставить `max-age=86400`.

## 2. Баги и логические дыры

### C3. Прямой supabase-режим отправляет несуществующие параметры

`booking_repository.dart:141-156` передаёт одновременно `p_segments`,
`p_starts_at` и `p_minutes`. PostgREST подбирает функцию по точному набору имён
аргументов — такой сигнатуры нет ни в одной миграции (ни в старой с
`p_station_ids`, ни в новой с `p_segments`). Результат: `PGRST202`, бронь падает
с «Неожиданная ошибка».

Прод это не задевает только потому, что `tool/build_web.sh` собирает с
`BOOKING_BACKEND=api`. Но дефолт в конфиге — `supabase`, то есть любая сборка
без флага молча ломается. Убрать две строки.

### C4. Админка не восстанавливает состав по часам

`AdminRepository.fetchRows` берёт `starts_at`/`ends_at` из `items.first` и
считает `headsets`/`consoles` по **всем** позициям заказа. Для брони
«12 шлемов первый час, 6 второй и третий» это даёт: длительность 1 час,
24 шлема. Сетка занятости нарисует ерунду.

Нужно: группировать `booking_order_items` по `(starts_at, ends_at)`, собрать
отрезки, восстановить `hourHeadsets` / `hourConsoles`, `startMinutes` = минимум,
`durationMinutes` = максимум `ends_at` − минимум `starts_at`.

### Прочее

- **Поля контактов не перерисовываются при внешнем изменении.**
  `contact_form.dart:100` создаёт `TextEditingController(text: widget.initial)`
  один раз. Вход по телефону (`_onAccountLoginSubmitted`) кладёт имя и телефон
  в стейт — но в полях остаётся старое. Нужен `didUpdateWidget` со сверкой.
- **`BookingConfig.sessionDurations = [30, 60]` — мёртвый код** с неверными
  значениями (реальные длительности — `BookingBloc.durations`, 60…300).
  Вводит в заблуждение при чтении конфига. Удалить.
- **Горизонт записи рассинхронизирован:** клиент видит 30 дней
  (`bookingHorizonDays`), админка — 120 (`AdminState.calendarDays`). Сотрудник
  создаст бронь на дату, которую клиент не увидит. Свести к одной константе.
- **`_kits()` подставляет выдуманные числа** для невыбранного клуба
  (`booking_view.dart:715`): V-Ray — «16 шлемов», Effect — «4 шлема».
  На первом экране карточки клубов показывают захардкоженный состав, пока клуб
  не выбран. Если состав в БД изменится — на витрине останется старое.
- **`hourCount` считается как `(durationMinutes / 60).round()`** — для 90-минутных
  сеансов (их нет в текущем списке, но они валидны в старых бронях) даст 2 часа
  вместо 1,5 и посчитает цену неверно.
- **Пакеты дороже почасовой оплаты** — известная нестыковка из `HANDOFF.md`:
  при VR 600 ₽/ч пакет «Компания» (4 шлема × 2 ч = 4800 ₽) стоит 10 000 ₽.
  Пакеты нужно либо переоценить в админке, либо скрыть до решения заказчика.
  Сейчас клиенту показывается заведомо невыгодное предложение.
- **Нет обработки истечения сессии в админке.** JWT Supabase живёт час; при
  протухшем токене запись упадёт с невнятной ошибкой в `state.saveError`.
  Нужен `onAuthStateChange` → `signedOut` → экран входа.
- **Нет `ErrorWidget.builder` / зоны перехвата.** Любое исключение в build даёт
  серый экран Flutter без объяснений и без телеметрии.

## 3. Адаптивность: телефон / планшет / ПК

### Что есть сейчас

Ровно **один** брейкпоинт на весь публичный виджет:

```dart
const double _wideBreakpoint = 860;   // booking_view.dart:33
const double _frameNarrow = 460;
const double _frameWide  = 1000;
```

То есть два состояния: «узкая колонка 460» и «две колонки 1000». Между ними —
ничего.

| Ширина | Устройство | Что происходит | Оценка |
|---|---|---|---|
| 320–374 | iPhone SE, старый Android | Рамка 460 схлопывается до ~288. Плитка станции фиксированные 74 px → в ряд влезает 3 вместо 4, ряд «ломается» | Работает, но плохо |
| 375–459 | Большинство телефонов | Основной сценарий, выглядит правильно | Хорошо |
| 460–859 | **iPad портрет (768), планшеты, телефон в ландшафте** | Рамка застывает на 460 → узкая колонка посреди пустого экрана, ~40 % ширины не используется | **Плохо** |
| 860–1000 | Ноутбук, iPad ландшафт | Две колонки, но рамка ограничена доступной шириной | Хорошо |
| >1000 | Десктоп, 4K | Рамка 1000, поля по краям | Хорошо |

### Конкретные проблемы

1. **Планшет = растянутый телефон.** Самая заметная дыра. Нужен средний
   брейкпоинт ~600 px с рамкой 600–720 и, возможно, слотами в 4 колонки.
2. **Плитка станции фиксирована на 74 px** (`hall_plan.dart:304`). На узких
   экранах ряд из 4 шлемов не влезает и переносится, ломая метафору «ряд зала».
   Нужен `LayoutBuilder`: ширина плитки = `(доступно − отступы) / 4`, с
   минимумом ~62.
3. **`SlotGrid` с `childAspectRatio: 1.55`** (`slot_grid.dart:54`) — жёсткая
   пропорция. При системном увеличении шрифта (accessibility, `textScaleFactor`
   1.3+) внутри 16 px + 11 px текста и точек гарантирован `RenderFlex overflow`.
   Нигде в проекте не используется `MediaQuery.textScalerOf` — весь макет
   свёрстан под масштаб 1.0.
4. **Нижний бар не липкий** — на длинной странице сумма и кнопка «Забронировать»
   уезжают за экран. На телефоне это бьёт по конверсии.
   ⚠️ Но «сделать sticky» нельзя в лоб: в iframe-режиме высота фрейма равна
   высоте контента, скроллит **родительская** страница, и Flutter про этот скролл
   не знает. Решение — либо липкость только в standalone-режиме
   (`window.parent === window`), либо отдельная плавающая кнопка, которую
   родитель позиционирует сам по событию `vr-booking:step`.
5. **`_leftColWidth = 360` фиксирован** — при ширине ровно 860 правая колонка
   получает ~390 px, что уже узко для сетки слотов.
6. **Админка непригодна на телефоне.** Ширина 1400, сетка занятости горизонтально
   скроллится, drawer `min(560, ширина)`. Для десктопа сделано аккуратно, но
   администратор с телефона (типовой сценарий для клуба!) работать не сможет.
7. **`manifest.json` — дефолтная заглушка Flutter:** `"name": "vr_booking_web"`,
   `"description": "A new Flutter project."`, `theme_color`/`background_color`
   синие `#0175C2` вместо тёмного `#08090A`, и `"orientation": "portrait-primary"`
   — при установке как PWA ландшафт на планшете будет заблокирован.
8. **Нет семантики для скринридеров.** Flutter Web в CanvasKit не строит
   accessibility-дерево, пока не запрошено. Виджет невидим для скринридеров и
   для парсеров. Как минимум — `SemanticsBinding.instance.ensureSemantics()`
   или сборка с HTML-рендерером для доступности.

### План адаптации

```dart
// вместо одного порога
const double _bpTablet  = 600;   // планшет / телефон в ландшафте
const double _bpDesktop = 900;   // две колонки

double _frameWidth(double vw) => switch (vw) {
  < _bpTablet  => 460,
  < _bpDesktop => 680,
  _            => 1000,
};
```

- 600–900: одна колонка, но шире (680), слоты в 4 колонки, плитки станций крупнее.
- Плитку станции и сетку слотов перевести на `LayoutBuilder` с расчётом от ширины.

Дизайн-система сама по себе сильная: единые токены `BookingColors`, акцент по
клубу, Archivo, консистентные радиусы. Дорабатывать стоит следующее.

1. **Контраст.** `textFaint #5B5B66` на `frame #101015` даёт ≈ 3.4:1 — ниже
   порога WCAG AA (4.5:1) для мелкого текста. Этим цветом набраны подписи-капсы
   и «Для сотрудников». `textOff #55555F` на занятых плитках — ещё хуже.
   Поднять на 2–3 ступени.
2. **Известная проблема из TODO:** на выбранной лаймовой карточке клуба
   «Ежедневно 11:00–22:30» почти не читается (`club_selector.dart`).
3. **Состояния фокуса.** Ни одного видимого focus-ring: навигация с клавиатуры
   по форме невозможна визуально. Для формы с полями ввода это обязательно.
4. **Нет скелетонов.** Загрузка — `CircularProgressIndicator` посреди пустоты;
   при смене даты/зала весь блок мигает. Скелетон сетки слотов убрал бы
   ощущение «сломалось».

   пилюли быстрого выбора (`PillButton`) заметно ниже 44 px — минимума для
   касания.
6. **Чек на экране успеха** — по `HANDOFF.md` пункт 5 редизайна («пунктирные

   неактивен, кроме мелкой строки-причины.

   перерисовывается скачком. Кросс-фейд 150 мс сделал бы связь «вкладка → план»
